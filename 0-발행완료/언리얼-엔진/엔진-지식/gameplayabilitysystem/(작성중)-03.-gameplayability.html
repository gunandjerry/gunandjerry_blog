(작성중) 03. GameplayAbility

개요

각각의 GA는 캐릭터의 독립된 행동을 표현한다. 예컨대 달리기, 점프하기, 총쏘기, 포션 마시기, 문 열기, 공격하기, 파이어볼 날리기같은 독립된 동작들은 모두 각각의 GA로 구현될 수 있다.
GA를 이러한 행동들을 캡슐화한 단위라고 볼 수도 있으며, 이렇게 만들어진 GA들을 키 입력이나 트리거를 통해 쉽게 발동시키고, 관련된 로직은 GA가 알아서 처리하도록 독립적으로 수행시키는 것이 핵심 개념이다.

GA는 발동 과정에서 꽤 많은 오버헤드를 발생시키기 때문에 단순한 함수 호출보다 훨씬 무겁다. 따라서 매 틱마다 수행되는 동작(기본적인 이동같은)은 GA로 만드는 것이 권장되지 않는다.

Note

예컨대 달리기를 GA로 구현한다면, 매 틱마다 MovementComponent에 이동량을 넣는 로직은 일반 함수로 처리하고, Sprint GA에선 Shift 키를 누르고 있으면 MovementComponent의 모드를 달리기로 바꿔 이동 속도를 증가시키고 스태미너를 감소시키는 식으로 구현하면 된다.

GA의 발동 과정

GA의 발동 주체는 ASC이며 행동 주체는 ASC의 AvatarActor가 된다.
GA를 발동하기 위해선 우선 ASC에 해당 GA를 '발동할 수 있다'고 부여해야 한다.

부여된 GA들은 언제든 발동될 수 있으며, 직접 GA의 타입을 명시하거나 핸들을 통해서 ASC에게 이 GA를 발동시키라고 시킬 수도, 트리거 태그를 달아놓고 HandleEvent로 태그를 전달하여 ASC가 해당 트리거 태그를 가진 GA를 발동하게 할 수도 있다.
혹은 특정한 ID와 바인딩할 수도 있다. 후술하겠지만 이는 특정 키와 GA를 간편하게 바인딩하여 범용 함수로 누른 키에 알맞은 GA를 발동시키기 위한 기능이다.

GA 실행 동기화 정책

GAS는 클라예측-서버검증 모델을 전제로 만들어진 만큼 GA의 발동 동기화에도 다양한 옵션이 제공된다.
GA의 Net Execution Policy가 이를 주관한다. Policy타입은 다음과 같다.

  • LocalOnly : 로컬에서만 GA를 발동시킨다.
  • LocalPredicted : 로컬예측-서버검증 모델을 사용한다.
  • ServerOnly : 서버에서만 GA를 발동시킨다.
  • ServerInitiated : 서버에서 먼저 수행한 후 클라에서 수행한다.

LocalPredicted가 기본이 되며 캐릭터의 행동을 캡슐화하는 GA의 설계 취지에 맞게만 사용한다면 다른 옵션을 사용할 이유는 웬만해선 없다.
GA 함수 내부에서도 HasAuthority나 IsLocallyControlled 함수를 통해 서버 권한이 있는지, 로컬 플레이어인지 확인할 수 있다.

GA 인스턴싱 정책

ASC가 GA를 발동시키면 해당 GA의 상태를 추적하기 위한 GA 인스턴스가 생성된다. 이 때 인스턴스를 어떻게 생성할 것인지에 대해서도 옵션을 제공한다.
InstancingPolicy가 이를 주관하며 타입은 다음과 같다.

  • NonInstanced : 상태 추적을 위한 인스턴싱 자체가 필요 없는 간단한 로직의 GA에서, GA의 UClass를 통해 수행하는 옵션. 언리얼 5.5 기준으로 사실상 Deprecated되었다.
  • InstancedPerActor : 하나의 인스턴스만 사용한다. 즉, 이미 GA가 발동중일 때 같은 GA를 발동하면 무시되거나 Retrigger된다.
  • InstancedPerExecution : 각각의 GA 발동마다 인스턴스를 생성한다.

다음은 가장 기본적인 실행 정책과 인스턴싱 정책을 설정한 GA의 호출부 코드 예시이다. 로컬예측-서버검증 모델을 사용한다고 알아서 로직에 대한 검증과 보정을 수행해주는 건 당연히 아니니 주의하자.

UGAPlayerAttack::UGAPlayerAttack()
{
	NetExecutionPolicy = EGameplayAbilityNetExecutionPolicy::LocalPredicted;
	InstancingPolicy = EGameplayAbilityInstancingPolicy::InstancedPerActor;
}

// 자세한 건 후술할 것이다.
void UGAPlayerAttack::ActivateAbility(...)
{
	...
	
	// 클라 -> 서버 순으로 실행될 로직
	
	if (IsLocallyControlled())
	{
		// GA의 발동 주체 액터가 로컬 컨트롤러에 빙의된 경우에만 실행되는 로직 
	}
	
	if (HasAuthority(&ActivationInfo))
	{
		// 서버에서 발동한 GA에서만 실행되는 로직
	}
}

GA 작성하기

GA의 발동 구조

  1. GA의 발동 시작
    • ASC->TryActivateAbility 류 함수를 직접 호출하여 GA의 UClass나 트리거 태그로 발동을 시도한다.
    • ASC->HandleGameplayEvent 함수로 트리거 태그를 전달해 발동을 시도한다.
    • ASC->AbilityLocalInputPressed 함수로 바인딩된 ID를 전달하여 발동을 시도한다. (이 경우, 이미 발동중이면 발동중인 GA의 InputPressed 함수를 호출한다)
두 방식의 차이

HandleGameplayEvent 함수도 내부적으로 TryActivateAbility를 거치지만, 커스텀 데이터를 전달하기 쉽다. TryActivateAbility류 함수들은 커스텀 데이터를 전달할 있는 매개변수가 없으며, ActivateAbility가 호출될 때 EventData에는 nullptr가 담긴다. 이 경우 커스텀 데이터를 전달하려면 GA 인스턴스에 직접 접근하여 집어넣는 우회적인 방법을 사용해야 하는데, 이는 강한 결합을 유발하므로 권장되지 않는다.

  1. 발동 가능 여부 판단

    • CanActivateAbility 함수에서 ASC에 부여된 GA의 핸들이 정상적인지, 쿨타임이 남았는지(CheckCooldown), 비용을 지불할 수 있는지(CheckCost) 검토한다. true를 반환하면 가능하다는 뜻.
    • CheckCooldown 함수와 CheckCost 함수도 오버라이딩 가능하다.

  2. GA 발동

    • 필요한 경우 전처리를 수행할 수 있게 PreActivate 함수를 우선 호출한다.
    • 메인 로직을 수행하는 ActivateAbility 함수를 호출한다.

  3. GA 비용 지불

    • (주로 ActivateAbility 내에서) GA를 수행한 대가를 지불한다.
    • CommitAbility 함수가 이를 처리한다. 내부적으로 쿨타임을 돌리기 위한 쿨타임 GE를 적용시키고(ApplyCooldown), GA의 비용 지불을 위한 비용 GE를 적용시킨다(ApplyCost)
    • ApplyCooldown 함수와 ApplyCost 함수도 오버라이딩 가능하다.
쿨타임, 비용 체크와 지불

CheckCooldown, CheckCost, ApplyCooldown, ApplyCost 함수의 기본 동작은 GA 클래스에 부착되어 있는 쿨타임 GE와 비용 GE를 '적용할 수 있는지' 체크하고, GA를 발동한 ASC에 '적용하는' 것이다.
기본 동작의 취지대로 작동하기 위해선 쿨타임 GE는 하나의 '쿨타임 태그'를 일정 시간동안 부여(Granted)하는 GE여야 하며, 비용 GE는 어떤 Attribute의 값을 감소시키는 GE여야 한다.
그럼 쿨타임의 경우엔 내부적으로 쿨타임 GE가 부착하는 태그가 현재 ASC에 존재하는지 체크함으로써 쿨타임이 지났는지 판단하며, 비용의 경우엔 비용 GE를 적용하여 감소되는 Attribute 중 0 이하가 되는 Attribute가 있다면 지불할 수 없는 것으로 판단한다.

  1. GA의 취소와 종료
    • GA 내부에서 CancleAbility가 호출되면 GA가 중간에 취소되었다는 뜻이다. 내부적으로 EndAbility를 호출한다.
    • GA 내부에서 EndAbility가 호출되면 GA가 종료되었다는 뜻이다. bWasCancelled 매개변수로 취소되어 종료되는 것인지, 정상적인 절차를 모두 밟고 정상적으로 종료되는 것인지 표시한다.

기타 주요 함수

앞서 발동 구조를 소개하며 설명한 필수 함수들 외에 주요한 기능을 수행하는 멤버 함수는 다음과 같다.

  • InputPressed, InputReleased : 상술한 바인딩된 ID를 누르거나 뗄 떼 호출된다. 누르는 경우엔 인스턴싱 정책이 InstancedPerActor이고, 이미 실행된 GA가 있다면 InputPressed 함수를 호출하고, 없다면 GA의 발동을 시도하게 된다.

AbilityTask

GA의 로직을 보다 쉽게 작성할 수 있게 도와주는 비동기 객체.

GA 사용하기

GA 부여하기

GA의부여는 서버에서 수행한다. 부여된 GA는 ASC를 통해 클라이언트로 전파되며, 클라이언트에서 부여하면 무시된다.

어빌리티의 부여는 어빌리티의 명세가 담겨있는 FGameplayAbilitySpec 구조체를 ASC에 등록하는 것이다.
ASC는 이 구조체를 통해 어빌리티를 관리하게 된다. 등록된(Activatable한) GA에 대해선 반환된 어빌리티 스펙 핸들을 통해 접근할 수 있다.
어빌리티가 발동되면 명세에 적혀진 대로 인스턴스를 생성한다.

단순 부여하는 GiveAbility 함수와 부여와 동시에 발동시키는 GiveAbilityAndActivateOnce 함수를 사용한다.

// TSubclassOf<MyGameplayAbility> abilityClass;
// int32 abilityLevel, abilityBindingInputID;
FGameplayAbilitySpec myAbilitySpec(abilityClass, abilityLevel, abilityBindingInputID);

ASC->GiveAbility(myAbilitySpec); // 스펙 핸들을 반환한다.

GA 박탈하기

// 스펙 핸들을 통해 제거한다.
ASC->ClearAbility(MyAbilitySpecHandle);

// 모든 어빌리티를 제거한다.
ASC->ClearAllAbilities();

// 특정 InputID와 바인딩된 어빌리티들을 제거한다.
ASC->ClearAllAbilitiesWithInputID(static_cast<int32>(MyAbilityInput));

// 해당 어빌리티의 발동이 끝남(EndAbility)과 동시에 제거한다. 해당 어빌리티가 현재 발동중이 아니라면, 즉시 제거한다.
ASC->SetRemoveAbilityOnEnd(MyAbilitySpecHandle);
