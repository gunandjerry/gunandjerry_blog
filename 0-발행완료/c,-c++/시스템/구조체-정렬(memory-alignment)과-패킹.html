구조체 정렬(Memory Alignment)과 패킹

개념

정렬(align)과 정렬이 필요한 이유

구조체의 구조 설계 규칙(또는 메모리 배치 규칙).
CPU는 데이터를 빠르게 읽기 위해 '데이터가 하나의 정렬된(일정한 크기의) 덩어리 안에 있다'는 가정 하에 복사하고 접근한다. 보다 구체적인 이유는 캐시라인의 크기나 버스의 전송 폭 등 여러가지 이유가 있지만 대충 CPU가 효율적으로 동작하기 위해 데이터를 덩어리로 다룬다고만 이해하면 된다.

더 구체적으론 바이트 단위로 매겨지는 주소와 자료타입들이 있을 때, 주소 % 크기 == 0이 되어야 효율적이라고 할 수 있다. 그래서 int32 변수가 시작되는 주소는 4바이트의 배수일 때, double 변수가 시작되는 주소는 8바이트의 배수일 때 유리하다. (이를 자연스럽게 정렬(naturally aligned)되어 있다고 한다.)
그래야지만 CPU가 그 4바이트 또는 8바이트를 통채로 읽을 수 있기 때문이다.

Note

심지어 어떤 CPU 아키텍쳐(ARM 계열 일부)에선 이렇게 정렬되지 않은 데이터에는 접근을 할 수조차 없다. (unaligned memory access)

따라서 정렬(align) 을 보다 쉽게 설명하자면 정해진 크기에 맞춰 데이터가 저장될 메모리 주소를 적절하게 선택하는 것이라고 할 수 있겠다. 어떤 구조체가 32비트로 정렬되어 있다면, 그 구조체 데이터가 놓이기 시작하는 주소는 반드시 32의 배수가 된다.

정렬의 관점에서의 구조체

구조체는 여러 데이터를 메모리 연속적, 집합적으로 관리하는 단위이다.
문제는 배열처럼 같은 크기의 같은 타입을 늘어놓는 거라면 고민할 필요도 없지만, 구조체는 여러 크기의 여러 타입들로 이루어질 수 있다는 것이다.

만약 개발자가 별 생각없이 아무렇게나 배치한 멤버들을 연속적으로 배치하면, 정렬되지 않은 형태가 되어 CPU가 읽는데 큰 애로사항이 생길 수 있다.
따라서 컴파일러는 강제적으로 멤버들 사이사이에 Padding byte를 끼워넣어 각각의 멤버들이 제대로 정렬될(적절한 주소가 배정될) 수 있도록 한다.

구조체 패킹

문제는 컴파일러 입장에선 개발자의 의도를 알 수 없으니, 그저 멤버가 선언된 순서대로 두고 그 사이에 Padding byte를 추가하는 동작만 수행한다는 것이다. 이 Padding byte는 많아지면 많아질 수록 당연히 공간의 낭비가 된다.

따라서 개발자는 구조체를 선언할 때 멤버들의 선언 순서를 적절히 배치하여 Padding byte가 최소화될 수 있는 효율적인 구조를 만들어야 하는데, 이를 구조체 패킹(Packing)이라고 한다.

네트워크 통신에서 구조체 패킹

구조체 정렬은 네트워크 통신에서 특히 중요해진다. 전달하는 패킷의 크기 자체의 비용 문제도 있지만 많은 서버들이 비용 문제로 리눅스를 사용하는데, 리눅스와 윈도우즈의 패킹 규칙이나 정렬 크기의 상한이 달라서 오류가 나는 경우도 있기 때문이다.

참고: SIMD와 하드웨어 I/O에서

최신 CPU 아키텍쳐의 기본 최대 정렬 단위는 16바이트인데, 이는 초기 SIMD 벡터 타입(__m128)을 포함해 primitive type의 최대 크기가 16바이트이었기 때문이라고 한다.
그런데 __m256 벡터나 _mm256_store_ps 함수처럼 더 큰 크기의 연산이 등장했고, 이런 SIMD 벡터나 연산을 사용하려면 해당 크기로 정렬 단위가 맞춰져 있어야 효율적이라고 한다. (그렇지 않으면 하나의 벡터를 여러 번 읽어야 하므로)

그리고 하드웨어 I/O에서도 종종 Direct Memory Access를 지원하기 위해 하드웨어 차원에서 특정한 크기로 정렬된 메모리 블록만을 읽을 수 있게 해둔 경우가 있다고 한다. 이럴 때도 강제로 정렬 크기를 맞춰 통신해야 한다.

구조체 패킹을 하는 법

컴파일러가 구조체를 정렬하는 방식

컴파일러는 일단 구조체의 멤버들을 보고 적절한 정렬 요구사항(alignment) 크기를 정렬의 기준 크기로 정하게된다. 이 기준 크기는 '구조체의 정렬'이 보장되는 최소크기로 정해지는데, primitive type들로만 이루어진 구조체면 대충 가장 큰 멤버의 크기와 같을 것이다.

예컨대 아래의 구조체는

struct Foo
{
	int i;
	char c;
	double d;
}

이런 식으로 d의 크기인 8바이트를 기준으로 멤버들을 하나씩 배치하다가, 다음 멤버를 연속으로 배치할 경우 정렬 기준 크기를 벗어나게 된다면 대신 padding byte를 채워넣고 다음 멤버를 배치하는 식으로 동작하게 된다.

이렇게 하는 이유는 이래야지만 구조체 인스턴스 각각에 대해서도 역시 정렬을 보장할 수 있기 때문이다.
간단한 예시를 들어보자.

struct Foo
{
	char c;
	int i;
}

Foo foos[10];

foos[n].c는 항상 1바이트로 정렬되어 있어야 하고, foos[n].i는 항상 4바이트로 정렬되어 있어야 한다. 정렬 기준 크기가 4바이트라 c(1바이트) -> 패딩(3바이트) -> i(4바이트)순으로 메모리에 놓여있다면 이게 잘 보장이 된다.
그런데 정렬 기준 크기가 1바이트라면? Foo는 메모리에 c(1바이트) -> i(4바이트)로 놓이게 되므로 foos[0]의 시작 주소가 0일 때 foos[1]의 시작 주소는 5가 되어버린다. 정렬이 깨져버리는 것이다.

Note

만약 구조체 내부에 구조체가 있다면, 내부의 구조체는 정렬된 그대로 하나의 묶음으로 취급되어 정렬된다.

정렬 기준 크기의 상한을 설정할 수 있다. 기본값은 8바이트로 보임.

코드로 패킹 규칙 설정하기

#pragma pack

C/C++ 컴파일러가 제공하는 전처리지시자로, 기본으로 설정된 패킹 크기보다 '더 작게' 패킹할 수 있게 해준다. (기본 패킹 크기보다 큰 값은 무시되고 기본 패킹 크기가 쓰인다)

alignof(type)

type의 정렬 크기(패킹 기준 크기)를 반환한다.
예컨대 alignof(float[10])은 정렬 크기가 4인 float들의 배열이므로 4를 반환한다.

alignas(size)

C++11에서 도입된 키워드로 구조체 단위로 패킹 크기를 설정할 수 있다.
pragma pack과 달리 압축을 강제하지 않으며, ABI 규칙과 컴파일러의 규칙에 따라 허용이 될 수도, 안 될 수도 있다.

struct alignas(4) foo
{
  int a;
  int b;
  char c;
};

struct alignas(8) bar
{
  int a;
  int b;
  char c;
};

가장 중요한 규칙은 '최소한 멤버들의 정렬 크기 중 가장 큰 것 이상이어야 한다'는 것. 예컨대 위 두 구조체에 alignas(1) 을 넣어봐야 무시된다.

std::align_val_t

C++17에서 추가된 매크로. 특별한 건 아니고 그냥 정수 타입인데 이 값이 '정렬 크기'로 쓰는 값임을 명시하기 위한 단위이다.
이 값이 '바이트 크기'임을 명시하기 위해 있는 size_t 같은 넘.
